FATHER — LLM Document Automation & Approval

Будущий автоматический конвейер: LLM готовит и проверяет документы, а полномочия и финальные gate остаются у ответственных ролей.

Главное правило

LLM не является финальным согласующим. Он может извлечь факты, привести документ к схеме, найти пробелы, противоречия, слабую трассировку и подготовить draft/gate recommendation. Но Legal applicability, Data ownership, Product authority, Architecture decision и Residual Risk Acceptance остаются за людьми/ролями с соответствующими полномочиями.

Что делает LLM

Intake Extractor

Разбирает секции, поля, факты, требования, ограничения, assumptions и UNKNOWN. Не заполняет отсутствующие значения догадкой.

Schema Mapper

Сопоставляет содержимое с полями конкретного артефакта и показывает unmapped/missing.

Traceability Linker

Предлагает связи source → claim → requirement → decision → verification. Не выдумывает source/clause refs.

Completeness Reviewer

Сравнивает документ с контрактом и формирует gap/questions register.

Conflict Reviewer

Выявляет противоречивые утверждения, версии и definition drift; хранит обе стороны до решения владельца.

Security / Normative Assistants

Предлагают applicability questions, abuse cases, threat drivers и missing evidence, но не выдают финальное Legal decision и не принимают residual risk.

Architecture Reviewer

Сравнивает варианты, строит trade-off matrix, выявляет unsupported “best” claims и готовит ADR draft.

Gate Assessor

Возвращает только suggestedGateOutcome и список blockers/conditions. Финальное gate-решение подписывает уполномоченная роль.

Что остаётся человеку

Business Owner / Product

Подтверждает проблему, scope, ценность, KPI, продуктовый gate.

Legal / Compliance

Финальная применимость правовых/регуляторных требований.

Data Owner

Классификация данных, допустимая обработка, sharing/retention.

Security

Security intake, threat model, security requirements; не подменяет risk owner.

Requirements / QA

Baseline требований, testability, acceptance evidence.

Architect + Independent Reviewer

Варианты архитектуры, решение, trade-offs; архитектор не self-approve material decision.

Risk Owner

Единственный, кто может принять остаточный риск в своей области полномочий.

Service / Release Owner

Release/operations gate, rollback, handoff, operational acceptance.

Маршрутизация по этапам

Product Discovery → Product/Business Owner → PRODUCT_READY
Security Intake → Security + conditional Legal/Data → SECURITY_INTAKE_READY
System Engineering → System + Integration + Security review → SYSTEM_MODEL_READY
Threat Model v0 → Security + System + Independent review → THREAT_MODEL_V0_READY
Requirements → Requirements + QA + domain authorities → REQUIREMENTS_BASELINE_READY
Delivery Feasibility → PM + Finance/Ops → DELIVERY_FEASIBILITY_READY
Architecture Options → Architect + Security + Skeptical Reviewer → OPTIONS_REVIEWED
Architecture Decision → Decision owner + Security + Independent review → ARCHITECTURE_DECISION_ALLOWED
Detailed Design → Software/API/Data/Integration + QA/Security → DETAILED_DESIGN_READY
Implementation → Engineer + Code Review + Security evidence → IMPLEMENTATION_VERIFIED
Verification → QA + Product/Security as applicable → VERIFICATION_COMPLETE
Release → Release/Ops → Service Owner → RELEASE_ALLOWED
Operation → Ops/Incident/Security → CONTINUE / REASSESS

Состояния документа

RECEIVED ↓ INGESTED → PARSED → EXTRACTED → CLASSIFIED ↓ MAPPED_TO_ARTIFACT_SCHEMA ↓ TRACEABILITY_CHECKED ↓ COMPLETENESS_CHECKED ↓ CONFLICT_CHECKED ↓ CANDIDATE_DRAFT ↓ OWNER_REVIEW ↓ DOMAIN_REVIEW ↓ INDEPENDENT_REVIEW ↓ APPROVED / CONDITIONALLY_APPROVED ↓ GATE ↓ FORWARD Любая проверка может отправить документ в REWORK_REQUIRED / BLOCKED / REJECTED.

Hard Blocks

  • нет accountable owner;
  • нет обязательного согласования;
  • blocking conflict не разрешён;
  • UNKNOWN превращён в факт;
  • source/evidence ref не разрешается;
  • material claim без provenance;
  • Legal applicability “утвердил” только LLM;
  • residual risk принял LLM или Security без risk authority;
  • архитектор self-approved material decision;
  • числовая цель/оценка выдана без требуемого basis.

Как это будет выглядеть в автомате

Inbox

Новые документы/версии, ещё не разобранные.

LLM Review Queue

Автоматические extraction / mapping / completeness / conflict jobs.

Human Approval Queue

Документы, ожидающие конкретную роль. Не общий “approve”.

Blocked

Показывает точный blocker, owner и downstream impact.

Gate Board

candidate outcome от LLM + финальный outcome от authority.

Trace Graph

Документ → claim → evidence → review → approval → gate → downstream.

Version/Diff

Что изменилось после прошлого согласования и какие approvals стали недействительны.

Audit

Кто/когда/почему согласовал, отклонил или отправил на доработку.

Будущая исполняемая схема

Document Store (immutable versions) ↓ events Work Queue / Router ↓ LLM Workers ├─ Extractor ├─ Mapper ├─ Trace Linker ├─ Gap Reviewer ├─ Conflict Reviewer ├─ Security/Normative Assistants └─ Gate Assessor ↓ Review Task Store ↓ Human Approval Queue ↓ Approval Records (append-only) ↓ Gate Engine ↓ Next-stage Router ↓ Notifications / dashboard / audit

Каждый LLM-run должен хранить trace ID, model ID, prompt version, input refs, output refs, duration и результат последующей human review.
