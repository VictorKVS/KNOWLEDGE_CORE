FATHER — Delivery Feasibility Workbench

Урок OTUS 2: от требований к измеримым NFR, плану, оценке, рискам, TCO и контролю изменений.

1. Зачем этот слой

До архитектуры мы не требуем финальную смету. Мы требуем доказательство, что проект можно осмысленно оценивать: требования измеримы, работа декомпозирована, неопределённость видима, риски назначены владельцам, а изменения контролируются.

Requirements candidate ↓ Measurable NFR ↓ Verification intent ↓ WBS v0 ↓ Estimate method + assumptions + range ↓ Project risks + risk buffer ↓ TCO / unit economics scenarios ↓ Change Management ↓ DELIVERY_FEASIBILITY_READY ↓ Architecture Options

2. NFR — не пожелание, а измеримое требование

Metric

Что именно измеряем: latency, throughput, quality, security, freshness, cost и т. п.

Target / Baseline state

Число только если оно подтверждено. Иначе TO_BE_BASELINED.

Priority

MoSCoW или иной явно выбранный механизм приоритизации.

Verification

Load test, eval, red-team, monitoring, manual/auto verification — метод должен быть известен до архитектурного выбора.

Источник урока: приложение A1 использует поля Category / Metric / Description / Target / MoSCoW / Verification Method. Учебные значения не становятся project defaults.

3. Discovery: вопросы, которые могут убить архитектуру

Business & Value

Проблема, пользователи, цена ошибки, наличие эталонного набора для проверки.

Data & Knowledge

Форматы, объём/рост, структурированность, чувствительные данные.

Infrastructure & Security

Cloud/on-prem ограничения, GPU, платформа, импортозамещение и обязательные ограничения.

Integration & UX

Системы интеграции, память диалога, streaming, agentic actions.

Process & Acceptance

Кто принимает работу, latency expectations, OpEx envelope, юридические ограничения.

4. Оценка — показываем метод, а не магическое число

Analogous

Сравнить с похожими работами и явно записать сходства/различия.

Parametric

Параметр × коэффициент; источник коэффициента и диапазон применимости обязательны.

PERT

Optimistic / Most Likely / Pessimistic → ожидаемое значение и диапазон. O/M/P остаются оценочными допущениями.

Bottom-Up

Декомпозиция до оцениваемых work items с последующим roll-up.

Анти-ошибка: точная дата или точная цена без метода, допущений и диапазона в FATHER считается ложной точностью.

5. WBS v0 — что именно предстоит сделать

Discovery / Design

интервью, данные, NFR, test/eval readiness

PoC

проверка ключевой гипотезы и decision gate

MVP Engineering

инфраструктура, data pipeline, backend, integrations

Production Readiness

load/security/monitoring/docs/support

Названия фаз из урока — шаблон для GenAI, не обязательный жизненный цикл FATHER. Канонические стадии остаются в lifecycle registry.

6. Project Risk Register

Risk

Data / Model / Security / Legal / Scope / External dependency / Delivery.

Probability & Impact

Числа допустимы как оценка, если есть основание. Иначе используем qualitative state.

Response

Avoid / Mitigate / Transfer / Accept + конкретный mitigation plan.

Trigger

Событие, после которого риск превращается в действие/эскалацию.

Project Risk Register связан с Security Risk Register, но это разные артефакты.

7. Change Request

Requested change ↓ Current vs desired baseline ↓ Requirements impact ↓ Architecture impact ↓ Security / Data / Operations impact ↓ Schedule + Budget + Risk impact ↓ APPROVE / REJECT / DEFER / NEED MORE EVIDENCE ↓ Versioned baseline update

8. TCO / Unit Economics v0

Cloud SaaS

CapEx, token/compute OpEx, support, licensing, uncertainty.

Self-hosted cloud

GPU rental, DevOps/MLOps, storage, support.

On-prem

hardware CapEx, energy, support, depreciation/procurement constraints.

Unit cost

Cost per request/call/document/user — только на явно заданных объёмных допущениях.

9. Gate: DELIVERY_FEASIBILITY_READY

PASS

Material NFR измеримы/имеют baseline plan; WBS v0 есть; метод оценки известен; риски, бюджетный диапазон, change model и verification intent существуют.

CONDITIONAL_PASS

Открытые вопросы не блокируют архитектурное сравнение и имеют владельца/условие закрытия.

BLOCKED

Нельзя оценить ключевой объём, скрыты зависимости, нет change control для FP или материал NFR невозможно проверить.

INSUFFICIENT_EVIDENCE

Недостаточно данных, чтобы честно определить реализуемость.

10. Что из OTUS не копируем как истину

Учебные числа latency/RPS/VRAM, размеры Golden Dataset, стоимости, проценты overhead и конкретные технологии из приложений — examples only. В FATHER сохраняется структура метода, а проектные значения должны иметь собственные sources/owners/evidence.
